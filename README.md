# CloudOps Sentinel

[![CI](https://github.com/BhavinGiridhara/cloudops-sentinel/actions/workflows/ci.yml/badge.svg)](https://github.com/BhavinGiridhara/cloudops-sentinel/actions/workflows/ci.yml)

CloudOps Sentinel is a production-inspired serverless incident-monitoring
platform built on AWS with Terraform. It accepts operational incidents through
an HTTP API, buffers them for asynchronous processing, stores a detection
record, and alerts operators when an incident is high priority.

## Architecture

![CloudOps Sentinel Architecture](docs/architecture.png)

~~~text
API Gateway -> Ingestion Lambda -> SQS -> Detection Lambda -> DynamoDB
                                      |                    -> SNS alerts
                                      -> dead-letter queue

EventBridge -> Health-check Lambda -> SQS
CloudWatch  -> dashboards, logs, and alarms
~~~

The queue separates request ingestion from downstream processing. The API can
return 202 Accepted after safely enqueueing a valid incident, while the
detection function scales independently and SQS absorbs traffic bursts.

## Reliability and security decisions

- The API validates all required fields before an incident enters the queue.
- Accepted severities are LOW, MEDIUM, HIGH, and CRITICAL.
- SQS partial-batch responses retry only failed records, not successful records
  from the same Lambda invocation.
- A message that fails processing three times is moved to an encrypted
  dead-letter queue for investigation.
- Each Lambda has its own IAM role. Ingestion and health checks can only send to
  SQS; detection can consume from SQS, write to the incident table, and publish
  to the alert topic.
- Deployment ZIPs are generated by Terraform from source and are not committed.
- GitHub Actions runs Python tests plus Terraform formatting and validation on
  pull requests and pushes to main.

SQS provides at-least-once delivery. DynamoDB writes reuse the incident ID, but
an alert can still be delivered more than once if a failure occurs after
publishing to SNS. A production extension would add explicit notification
idempotency.

## Incident flow

1. A service submits an incident to POST /incidents.
2. API Gateway invokes the ingestion Lambda.
3. The function parses the JSON body and validates service, incident_type,
   severity, and message.
4. A valid incident receives an ID and UTC timestamp, then is sent to SQS.
5. The detection Lambda consumes queued incidents and stores them in DynamoDB.
6. HIGH and CRITICAL incidents are published to SNS.
7. Failed SQS records are retried independently and eventually routed to the
   dead-letter queue.
8. EventBridge sends a synthetic health-check incident through the same queue
   every five minutes.
9. CloudWatch records logs and metrics and raises operational alarms.

## Example request

~~~powershell
$body = @{
    service       = "checkout-api"
    incident_type = "CheckoutOutage"
    severity      = "CRITICAL"
    message       = "Customers cannot complete checkout"
} | ConvertTo-Json

Invoke-RestMethod -Uri "https://<api-id>.execute-api.us-east-1.amazonaws.com/incidents" -Method POST -ContentType "application/json" -Body $body
~~~

Successful response:

~~~json
{
  "message": "Incident accepted",
  "incident_id": "generated-incident-id",
  "sqs_message_id": "generated-message-id"
}
~~~

Invalid requests return 400 Bad Request with field-level errors and are not
queued.

## Testing

The unit suite covers API validation, incident normalization, SQS failures,
severity-based alerting, multi-record batches, and partial batch failures.
AWS calls are replaced with small in-memory fakes, so no AWS account is needed.

~~~bash
python -m pip install -r requirements.txt
python -m pytest -q
~~~

Validate the infrastructure locally:

~~~bash
cd infrastructure/environments/dev
terraform fmt -check -recursive .
terraform init -backend=false
terraform validate
~~~

## Monitoring

CloudWatch tracks:

- API Gateway requests and 5XX errors
- Lambda invocations and errors
- SQS queue depth
- SNS notifications

Configured alarms notify operators when a Lambda fails, the API returns a
server error, or the incident queue develops a backlog.
